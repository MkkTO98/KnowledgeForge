# Deterministic Validator Taxonomy Specification

Date: 2026-07-09
Status: architecture specification; implementation not authorized

## 1. Purpose

KnowledgeForge validators must be deterministic, narrow, explainable, and tied to explicit constitutional or package contracts. They classify issues rather than hiding them behind a single pass/fail state.

This taxonomy specifies categories, severity, and default blocker behavior. It does not implement validators.

## 2. Severity levels

| Severity | Meaning | Default effect |
| --- | --- | --- |
| Blocker | Violates constitution, contract, provenance, reproducibility, or boundary required for acceptance. | Package cannot be accepted or promoted. |
| Warning | Indicates risk, incompleteness, advisory concern, or future maturity gap. | Package may remain candidate or accepted only if policy allows and rationale is recorded. |
| Advisory | Non-blocking recommendation, optimization, or future improvement. | No lifecycle block; recorded for planning. |
| Environment issue | Tooling/file/system condition prevented verification. | Does not prove package invalid; blocks claims that verification passed. |

## 3. Validator categories

### V1. Constitutional boundary violations

Detects violations of KnowledgeForge's non-negotiable boundaries.

Examples:

- package owns external observational data as KnowledgeForge data;
- package generates interpretation, insight, forecast, recommendation, presentation narrative, or autonomous action;
- package treats graph/database/API representation as defining abstraction;
- package bypasses evidence/provenance/lifecycle/governance requirements.

Default severity: Blocker.

### V2. Evidence contract violations

Detects missing or malformed evidence references/evaluations.

Examples:

- evidence class missing;
- source family missing;
- evidence reference and evaluation collapsed into one field;
- unsupported LLM output treated as evidence;
- manual evidence lacks source identity or capture information;
- contradiction search required but absent.

Default severity: Blocker for accepted/supported packages; warning for early candidate drafts when explicitly marked.

### V3. Provenance violations

Detects missing provenance envelope elements.

Examples:

- missing package creator/date;
- missing source version/vintage/access date;
- missing model/template identifiers when used;
- missing generated intermediate retention reference;
- missing prior revision for changed object.

Default severity: Blocker for accepted packages.

### V4. Reproducibility violations

Detects inability to replay, audit, or explain generation.

Examples:

- missing computation recipe;
- missing query definition;
- mutable live source referenced without snapshot when reproducibility required;
- nondeterminism not declared;
- generated package lacks manifest fingerprint.

Default severity: Blocker for derived/statistical/accepted generated packages; warning for manually preserved historical evidence when explicitly scoped.

### V5. Unsupported inference violations

Detects claims that exceed evidence or enter downstream interpretation territory.

Examples:

- correlation stated as causality without separate sourced causal claim;
- data characterization stated as macro interpretation;
- evidence evaluation turned into investment implication;
- hypothesis generated by KnowledgeForge rather than preserved from source;
- broad applicability claimed from narrow evidence.

Default severity: Blocker.

### V6. Package schema violations

Detects missing required package sections or invalid fields.

Examples:

- no package identity;
- missing status/lifecycle/governance state;
- invalid package kind;
- missing generated statement identifiers;
- invalid governed vocabulary value.

Default severity: Blocker for package acceptance; warning for incomplete draft if clearly marked draft.

### V7. Lineage/fingerprint inconsistencies

Detects mismatches among inputs, fingerprints, generated outputs, and lineage.

Examples:

- package fingerprint does not match manifest;
- input fingerprint changed without evolution report;
- query hash changed but computation method version unchanged;
- generated statements changed without package version update;
- source evidence handle no longer resolves or conflicts with recorded fingerprint.

Default severity: Blocker unless explicitly recorded as an environment/resolution issue for investigation.

### V8. Maturity-state violations

Detects packages or workflows claiming a maturity/lifecycle state not supported by evidence.

Examples:

- package marked accepted while validator blockers remain;
- local-model-assisted workflow marked deterministic replay;
- production-governed status claimed from one fixture;
- lifecycle transition lacks review rationale.

Default severity: Blocker for state promotion; warning for planning reports.

### V9. Advisory warnings

Detects non-blocking quality issues.

Examples:

- evidence source is stale but scope is historical;
- confidence label too coarse but not required for current lifecycle;
- package lacks optional downstream-readiness metadata;
- future review recommended because dependency changed outside applicability scope.

Default severity: Warning or advisory.

### V10. Repository/governance consistency checks

Detects file-backed ProjectForge operating discipline issues.

Examples:

- task artifact not updated;
- state/handoff stale;
- report missing from summaries;
- architecture-reality audit stale after architecture change.

Default severity: Warning for ordinary docs; blocker when claiming task closeout or implementation readiness.

### V11. Tooling/environment issues

Detects cases where verification could not run.

Examples:

- missing command;
- dependency unavailable;
- permission denied;
- external service unavailable;
- path missing due to environment difference.

Default severity: Environment issue. It blocks claims of successful verification but does not automatically invalidate architecture.

## 4. Classification output contract

Validators should eventually emit structured findings:

- category;
- severity;
- object/package/path;
- violated rule;
- evidence/context;
- remediation suggestion;
- whether acceptance is blocked;
- whether issue is repository inconsistency, governance inconsistency, tooling/environment issue, or knowledge-package issue.

## 5. Validator implementation priorities

Recommended order:

1. package schema and constitutional boundary checks;
2. evidence/provenance separation checks;
3. fingerprint manifest checks;
4. unsupported inference language checks;
5. lifecycle/maturity-state checks;
6. repository/governance consistency checks.
